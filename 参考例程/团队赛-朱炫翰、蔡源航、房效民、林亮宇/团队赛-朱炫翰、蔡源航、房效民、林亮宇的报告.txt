第 2 章 系统详细设计
2.1 系统整体架构设计
前端可大致划分为分支预测模块和取指模块，分支预测模块包含 FTB、TAGE、
RAS、预译码等模块，取指模块取指宽度为 4，每周期最多向指令缓冲填入 4 条指
令。由于采用了精度较高的 TAGE 分支预测器，前端的预测准确率能达到 95%左
右（单次 bitcount test 测试结果）前端各个组件的作用和交互时序将在下面介绍。
后端从流水线阶段上看大致分为译码阶段、重命名阶段、发射阶段、执行阶段
和提交阶段，从功能上看包含译码器（decoder）、指令缓存队列（IB）、重命名映
射表（RAT）、指令发射队列（IQ）、功能执行单元（FU）、分支跳转单元（BU）、
乘法器、除法器和重排序缓存（ROB）。指令执行过程大致如下：1.译码阶段，从
IB 中取出两条指令进行初步译码；2.重命名阶段，指令查询 RAT，记录源寄存器
对应的 ROB 索引，同时将目的寄存器对应的 ROB 索引写入 RAT。重命名结束后
将指令填入 IQ 和 ROB；3.发射阶段，从 IQ 中顺序取出两条指令，根据指令记录
的重命名关系，查询 ROB 确认数据是否准备完毕，当数据准备完毕且可以正常流
入下一个流水级时，将指令发射出去；4.执行阶段，指令在对应的 FU 中进行相应
的算术、访存操作。指令执行完毕后，将数据存入 ROB 中等待退休；5.提交阶段，
检查 ROB 队列顶部的两条指令是否满足退休条件，满足则让指令进行退休，进行
相应的写寄存器堆、写 csr、异常处理等操作。
2.2 前端设计
处理器前端采用取基本块结构，主要包括分支预测器（BPU），取指目标队列
（FTQ）和取指令单元（IFU），预译码模块（Predecoder）。
2.2.1 分支预测器
分支预测器每周期最多对一个地址进行预测，生成的预测块最多包含 4 条指
令，出于取指单元设计复杂度考虑，预测块会在跨行处截断。
分支预测器核心组件包括 uBTB、FTB、TAGE，实现了条件分支指令、函数调

L0：

主预测器重定向信号和新的预测块。
2.2.1.2 取指目标缓冲 FTB：
FTB 功能：
用于存储含有分支的预测块信息，存储的信息较多，使用 BRAM 实现以优化
板上资源。规格为 4 路组相连，每组 1K 项，使用 pc 的第 3 至 12 位进行索引，pc
的 13 至 32 位作为 tag 精确匹配。通过预测块的开始地址来查询 FTB 的表项。
FTB 条目内容：
tag（由预测块开始地址决定）
fall-through address（分支不跳转情况下的顺序执行地址）
jump-target address（分支跳转目标地址）
branch-type（分支指令类型）
FTB 更新的时机：
因为 FTB 中的信息是整个前端推测执行的基础，必须保证其正确性，所以只
有当分支指令所在的基本块在后端进行提交时才将分支信息推入 FTB 进行更新。
FTB 更新的条件：
当基本块中出现，非条件分支、条件分支第一次跳转、分支指令跳转信息错误
这三种情况中的一种时，将基本块作为 FTB 的一个条目写入 FTB 或者对 FTB 条

2.2.1.3 简单预测器 uBTB：
当拍返回的简易预测器，提供基础无空泡预测块（默认取指宽度 4，跨行截断）
由于 FTB 只有在基本块提交时才进行信息的更新，当分支指令在后端向前端
发出重定向后，还需要至少 3 个周期才能通过后端提交更新到前端 FTB 中。对于
往回跳转的小循环，由于 BPU 的预测流水线速度很快，容易出现 FTB 信息还未更
新，BPU 就已经对发出重定向的分支指令进行预测的情况，也就是主预测器会在
循环中丢失一次预测。
针对这个现象，uBTB 被设计为一个只有 16 个条目，采用 pc 第 3 至 6 位作为
索引，高 26 位作为 tag 精确匹配的缓冲。当后端向前端发出分支重定向时，uBTB
立刻根据分支跳转的目标 pc 和分支指令 pc 判断，如果是往回跳转的分支，就向
uBTB 中填入一个有效条目。
当 uBTB 条目命中时，会根据当拍返回的跳转目标产生一个跳转的预测。如果
FTB 中存有同一条跳转指令的 pc，那么下周期 FTB 命中，将根据主预测器给出的
预测信息覆盖上一周期 uBTB 产生的基础预测。
2.2.1.4 返回地址栈 RAS：
返回地址栈分为两个栈，32 个条目，分别由前端和后端各自维护。
当 FTB 命中了一条调用指令时，主预测器将调用入口地址作为预测目标，同
时将调用指令的返回地址压入前端维护的 RAS。当 FTB 命中了一条返回指令时，
从 RAS 中取出返回地址。
后端如果执行了调用指令或者返回指令，会自动维护 RAS，保证后端维护的
栈一定是正确的。如果后端向前端发出重定向，那么用后端维护的 RAS 去恢复前
端的 RAS。当同一个函数在不同地方进行调用时，前端总是能对函数调用的返回
做出正确的预测。
2.2.1.5 主预测器 TAGE
TAGE 预测器是专门用于预测条件分支指令跳转方向的二级预测器表，其预
测结果需要在下一拍才能返回。该预测器的规格如下：基础预测器包含 8K 项，每

2.2.2 取指目标队列 FTQ
FTQ 模块的主要功能是作为分支预测模块与取指模块之间的缓冲区，负责存
储预测信息，并且接收来自后端提交的训练数据，送回用于分支预测的训练。
当 BPU 模块接收到来自 PC 的查询请求时，在默认预测不发生跳转的情况下，
会在当拍将预测取指块发送至 FTQ 中，确保取指流程的顺畅进行。如果下个周期
主预测器给出有效预测，会将上个周期发送至 FTQ 的取指块修改。在我们的 CPU
中，FTQ 队列的大小是 8，考虑到每一个块最多有 4 条指令，所以前端最多等待后
端提交 32 条指令，这与后端 ROB 条目的数量是相同的。
2.2.3 取指令单元与取指流水
IFU 每周期从 FTQ 中读取预测块，进行地址翻译，如果没有出现相关异常，
那么向 Icache 发出取指令请求。
取指流水：
L0 读预测块：
从 FTQ 中读出预测块，将预测块起始地址送入地址翻译单元进行翻译，当拍
接受地址翻译的返回结果并存入寄存器中。
L1 发取指请求：
对 L0 地址翻译的结果进行处理，使用物理地址向 Icache 发送取指请求，如果
出现异常则不进行取指。
L2 等待指令返回：
等待 Icache 将指令返回。由于 Icache 可能在不定周期返回指令，因此前端维
护了一个和 Icache 返回指令有效同拍的信号表明读事务有没有完成。当后端发出

2.3 指令缓冲（IB）模块设计
使用指令缓冲来实现前后端的解耦，从而使前端取指和后端执行互不干扰。在
模块中实例化一个 FIFO 作为指令缓冲队列，从前端取回 1-4 条指令存入队列中，
执行时取出两条指令进行译码。FIFO 中的一条信息包含了：指令有效位、指令的
PC 值、指令的二进制码、分支预测的信息以及例外信息。队列的判满逻辑采用灵
活判满，即根据前端取回的指令数量判断队列是否为满。当队列满时，会暂停前端
取指，当队列空时，向译码阶段发送的指令有效位为 0，即相当于发射空指令，以
此来保证前后端工作的独立性。
2.4 后端设计
2.4.1 译码模块设计（ID）
译码模块每周期从指令缓冲中取出两条指令进行译码，实例化两个译码器，分
别对两条指令译码产生执行过程所需的控制信号、立即数。在该模块检测指令不存
在例外，并将此例外信息附在指令上，和指令 pc 值、分支预测信息、控制信号、
立即数等作为译码结果传递至下个流水级。
2.4.2 重命名映射表模块设计（RAT）
该模块拥有 4 个读端口、2 个写端口和 2 个无效化端口，内部存储分为两
个部分：1.32 位的寄存器 valid，每一位对应一个逻辑寄存器的映射关系是否有效；
2.32 × log2(ROB_DEPTH)的寄存器数组 prf，每一项记录着一个逻辑寄存器映射到
的 ROB 索引。

在重命名阶段，若指令需要写寄存器堆，则以其目的寄存器为 RAT 索引，将
对应位的 valid 置 1，将对应位的 prf 记为该指令所在的 ROB 索引；若指令需要使

前一条指令的 ROB 索引作为源寄存器的 prf 值，且 valid 为 1。
在提交阶段，当指令退休时，需要以其目的寄存器为 RAT 索引，如果对应位
的 valid 值为 1 且 prf 值等于该指令的 ROB 索引，意味着这一映射关系一直存在，
没有被后面指令的重命名所修改，然后就将对应位的 valid 置 0 即可。
2.4.3 重命名模块设计（RA）
指令进入重命名模块后，需要查询重命名映射表和重排序缓存完成重命名。指
令先查询重排序缓存，获得指令将要被放入的 ROB 索引。接着如上一部分所述查
询和写入重命名映射表，获得指令源寄存器的映射关系。最后准备好放入 IQ 和
ROB 的数据，在 IQ 和 ROB 都未满时将数据送入 IQ 和 ROB。
2.4.4 发射模块设计（ISS）
发射模块每周期从 IQ 中顺序取出两条指令，先根据指令类型判断能否进
行双发射：1.两条指令发生写后读冒险；2.同时有两条访存指令 3.同时有两条乘除
法指令；4.前一条指令为分支跳转指令；5.两条指令中存在特权指令；6.前一条指
令发生了例外；7.前一条指令被打上重取标记时，进行单发射，其他情况在 FU 使
用不冲突的情况下进行双发射。
接着判断一条指令能否发射，主要是看其源操作数是否已经准备好。指令
根据其源寄存器的映射关系查找 ROB，ROB 返回 complete 信号（表示数据是否准
备好）以及 32 位数据。数据准备好后根据指令类型和 FU 的使用情况将指令发射
到相应的 FU 中执行。
在部分情况下需要阻塞指令的发射：1.前面指令的执行过程中发现了例外
和重取信号；2.BU 中的分支跳转指令发现需要进行重定向；3.已经发射且未提交
的指令中存在写 csr 的指令。

2.4.5 执行模块设计（EXE）
执行模块内部实例化了 4 个不同的 FU 和 1 个 BU 作为指令执行单元。FU0 和
FU1 作为普通指令的执行单元、FU2 作为访存指令和特权指令的执行单元、FU3 作
为乘除法指令的执行单元、BU 作为分支跳转指令的执行单元。指令执行完毕后，
将数据写入指令 ROB 索引对应的位置，同时将对应位置的 complete 信号置为 1，
表示指令已经执行完毕。
2.4.6 重排序缓存模块设计（ROB）
该模块内部实例化一个 FIFO 作为存储部分，每一项储存一条指令退休时需要
使用的数据，包括指令 pc 值、指令执行结果、访存地址、特权指令相关信息、分
支预测信息和异常信息等。
在重命名阶段，指令读 ROB 返回指令将要放入的 ROB 索引，并在进入 ROB
时将对应位的 complete 信号置 0，表示指令未执行完毕。
在发射阶段，指令根据源寄存器的映射关系读取 ROB 对应位的 complete 信号
和数据。
在执行阶段结束时，指令将执行结果存入 ROB 对应位置处，并将对应位的
complete 信号置 1，表示指令执行完毕。
在提交阶段，ROB 将允许退休的指令数据送至提交阶段，将退休指令的目的
寄存器和 ROB 索引送至 RAT 进行无效化，然后在下一时钟上升沿修改头指针，完
成指令的出队。
当分支预测错误发生重定向时，将 ROB 尾指针修改为该分支预测指令的 ROB
索引处，实现分支预测错误后 ROB 的恢复工作。

2.6 cache 设计
2.6.1 icache 设计
本处理器的 icache 设计采用四路组相连阻塞式状态机设计，设计思路以及信号
命名参考 LoongArch 版 CPU 设计与实战。参考存储采用 block memory 作为存储
模块，icache 大小为 16KB，使用 VIPT 查询方式，主存块标记 tag 为 20 位，cahce
索引地址 index 为 7 位，字块内偏移 offset 为 4 位，因此一个 cache 行可以存储 4
个字。Icache 替换策略为无效路优先的随机替换。
Icache 支持每次从 cache 中取出一行数据交给前端处理，如果不命中，则向总
线发读请求。
单 cache 行查找的状态机转换：
IDLE：初始状态，处理完取指请求后保持的状态。若发出取指令请求，同时没
有 cacop 请求，进入 LOOPUP 查找状态，并在此时将查找 index 地址等送入 cache
行进行查找比对，以便能在下一个周期返回比对结果，否则保持在原状态。
LOOKUP：查找阶段，根据上一个周期传入的地址得到的数据块判断是否命中，
若命中，则直接返回一行 cacheline 数据，并检查 valid 是否置高，如果置高，则说
明又有访存请求的发出，状态机仍为 lookup，如果没有 valid 的发出，则直接返回
到 IDLE 状态。
如果 cacheline 没命中，状态机转换到 miss 阶段，进行后续的选择路替换。
Miss 阶段：等待 wr_rdy 置高，同时根据替换策略选取替换路，等待下一个阶
段发出，下一个阶段进入 replace 阶段。
Replace 阶段：发出读请求，根据替换块是否为脏决定是否发出写请求。同时
等待 rd_rdy 置高，如果 rd_rdy 置高时，状态机转换到 Refill 阶段。
Refill 阶段：等待读总线返回数据，内部有一个 ret_cacheline 寄存器，用来存

2.9 VGA 控制器
2.9.1 VGA 控制器设计
本系统实现了一个基于异构计算架构的高性能、无撕裂 VGA 显示控制器。其
核心是一个由多个专用硬件 IP 核构成的并行处理流水线，通过 AXI4 互联架构协
同工作，实现了从内存到屏幕的端到端硬件加速数据通路。
运行阶段始于帧缓冲读取控制器的启动。该控制器作为主设备发起高效的
AXI4 突发读事务，以最大化内存带宽利用率的方式从 DDR 系统内存中获取原始
图像数据。读取的数据被实时重组为符合 AXI4-Stream 协议的视频流，其中嵌入的
TUSER 信号标识帧起始，TLAST 信号标识行结束，从而维持了视频流的时空结构。
视频流随后进入流处理器进行实时处理。该处理单元在像素级流水线上执行
可配置的图像处理算法，可能包括但不限于色彩空间转换、分辨率缩放、以及基于
查找表的色彩校正。处理过程以线速进行，确保了恒定的处理延迟，从而满足了实
时显示系统的时序要求。
经处理后的视频流被馈送入帧缓冲写入控制器。该控制器同样作为 AXI4 主设
备，将处理后的像素数据以突发写事务形式写入指定的后台帧缓冲区。此过程严格
遵循双缓冲机制：显示控制器（axi_tft）始终从前台缓冲区读取数据以驱动显示设
备，而视频处理流水线则向后台缓冲区写入处理完毕的下一帧图像。这种隔离机制
从根本上消除了读写竞争导致的屏幕撕裂现象。
缓冲区交换是系统的关键同步操作。当一整帧数据完全写入后台缓冲区后，系
统通常会在垂直消隐期（Vertical Blanking Interval）——即前一帧显示结束、后一
帧尚未开始的时序窗口——通过 CPU 干预或直接内存访问（DMA）触发一次原子
性的指针更新。具体而言，CPU 将 TFT 控制器的帧缓冲区基地址寄存器重新映射
到已完成写入的后台缓冲区地址。此后，原先的后台缓冲区晋升为新的前台缓冲区
用于显示，而原先的前台缓冲区则变为新的后台缓冲区，接收后续处理流程的输出，
从而完成一个完整的处理与显示周期。
最终，TFT 显示控制器独立工作。它基于预先配置的 VGA 时序参数（包括水

第 5 章 关键问题及解决方案
我们遇到的关键问题基本上是系统启动过程遇到的问题，这部分已经在前面
详细说明，接下来我们只讲一下在设计调试过程中积累的经验和运用的思想。
首先下一个定论，调试过程中遇到的 90%的问题都必需依赖仿真进行解决，
如果没有仿真，那么解决问题将变得非常麻烦棘手，所以遇到问题还是优先想想能
不能通过仿真测试解决，即使没有直接的仿真手段，也要思考能不能找到相关问题
的仿真测试来间接检验。
CPU 上板后的情况非常复杂，上板后的问题不一定都能找到对应的仿真测试
（例如前面提到的 PMON 启动过程中遇到的问题），此时该怎么办呢？这时候就
要学会从一个高层次去看待问题，逐步缩小问题的范围，然后对怀疑出问题的模块
和功能进行不同场景下的针对性仿真测试，可能会找到解决问题的办法。
拿我们系统调试的过程来举例子，在调试过程中我们逐步明白 CPU 可以大体
上分为两个模型：流水执行模型+访存模型
流水线执行模型指的是从前端取指令到指令被分发到后端执行，最后在后端
执行完毕进行提交。流水线执行模型中需要做到正确处理以下几种情况：
pc 值没有产生异常时前端能否正确将指令取回。
前后端在出现分支重定向时能否正确进行冲刷，并且保证不会将错误的指令
进行提交。
后端执行过程能保证指令得到正确的操作数（主要与后端前递逻辑有关），完
整实现指令的功能（尤其特权态指令的正确实现）。
CPU 执行过程中产生的异常指的是在正确的指令流中的异常，如果一个异常
本身属于错误指令流（会被分支重定向修正），那么不需要处理这个异常。
……
对于访存模型，由于比赛要求实现 Cache 和 AXI 总线，同时启动系统又一定
要实现地址翻译和 TLB，因此访存模型虽然功能单一，却是一个非常复杂的系统，

如果前期设计产生疏忽，很难保证在实际的复杂访存行为下总是正确的。访存模型
主要在于做到以下几点：
给出正确的地址，能否将指令/数据取回。
出现访存相关异常（地址异常，tlb 异常），能否正确处理异常。
如果访存时禁用缓存，那么 CPU 内部相应的模块（可能由 Cache 一并实现）
能否正确绕过缓存取回数据。
向 AXI 总线发出的请求和进行的处理是否正确（对于外设来说非常重要）。
如何保证缓存 CACOP 处理的正确性。
……
在 CPU 设计过程中，我们首先采用面向测试用例的敏捷开发模式，分不同阶
段逐步实现指令，通过简单测试用例初步验证功能是否正确，但是此时进行的测试
是不全面的，甚至可以说是漏洞百出的。在实现指令的过程中不能认为跑通功能测
试就万事大吉了，但是在这个阶段 CPU 功能还非常羸弱，指令没做完大部分仿真
测试都不能跑，因此也只能依赖功能测试硬着头皮往下做，这个过程中缺陷会一点
点积累，直到在调试系统的过程中集中爆发。
说回前面提到的流水线执行和访存模型，在 CPU 设计的过程中，由于每个
阶段都要运行功能测试，而无论什么测试都要求流水线功能正常，能保证各种情况
下指令正常执行（要不然根本就跑不起来嘛）。尤其是当 CPU 能顺利通过官方提
供的性能测试时，此时我们认为流水线内部其实具备了较强的鲁棒性，对于正常情
况下执行用户态指令一般不会出现错误。如果是流水线相关缺陷，大概率可能在处
理异常时会出现问题（因为对异常处理的测试比较少）。异常处理相关的问题一般
修复起来比较简单，甚至大部分的异常处理错误来源于对指令手册、参考核等相关
资料理解不到位。
对于访存模型，由于加入 Cache 和地址翻译之后整个访存系统的复杂度非常
高。《实战》中引入 Cache 之后，虽然对 cacop 指令设置了专门的测试点，但是总
得来说测试数量还是太少，实际上板遇到 cacop 指令还是很容易出现错误。而对于
uncache 访问，《实战》压根就没有提供专门的测试来进行，而 uncache 访问往往

和外设相关，而外设功能是否正常在上板之后其实非常关键。总之，通过《实战》
和 chiplab func 完成指令功能后，其实访存模型存在缺陷的可能性是很大的。我们
在启动系统的整个过程中，大概 75%的问题都和访存有关，而且一旦问题和访存
相关，就变得极难排查（从前文就可以看出来，非常地困难且煎熬）。
我们后期在调试系统过程中遇到问题，通常采取的办法是：把 uncache 信号拉
高，先让 CPU 禁用 cache 跑一下。前面已经提到过流水线执行已经很鲁棒，我们
一般不优先考虑流水线出现问题，把 uncache 一直拉高然后跑各种仿真测试大概率
能排查出 uncache 访存的缺陷并且修复。那么此时 CPU 相当于抛弃 cache 在“裸
奔”，我们应当对此种情况下 CPU 的稳定性具有信心。
如果禁用 cache 后能通过出问题的地方，那么就可以把问题定位到 cache 内部，
如果在同一个位置出错，此时优先考虑总线行为不正确，然后再考虑流水线的异常
处理有缺陷，最后才考虑用户态指令执行过程中出现问题（这是在没有波形的情况
下进行的推测，如果有波形直接分析修复即可）。
通过这个办法能大致对缺陷进行定位，如果用同样的思想继续对 CPU 根据功
能进行划分，还能进一步将流水线分割为前端和后端分别看待，总之通过假设加上
验证的办法一步一步将出现问题的范围缩小，直到没办法将问题的范围缩的更小
就可以开始全面筛查。这就好像对问题进行“降维打击”，如果不采用这种办法尝
试直接修复问题，免不了越来越狭隘，不仅可能被一个缺陷困住好几天，而且还可
能耽误了其他功能的测试完善。

6.2 未来展望
在我们架构的基础上，首先最显而易见的是做流水式 Cache 把取指效率翻倍，
这样应当能较大地提升 IPC，同时后端因为有 ROB，做乱序发射是没问题的，并
且今年比赛上科大通过引入 L2 cache，在一些访存压力比较大的性能测试点上取
得了非常好的效果（一举击败清华夺得特等，128KB 的 L2 大缓存能把所有测试数
据都兜住了），因此如果要在我们的架构上优化的话，我推荐优先提升前端效率，
其次是认真做好 L2 Cache（这个缓存一致性问题还是很难解决的），最后是后端
改出乱序，其中 L2 Cache 需要耗费较大的精力但是性能测试中的回报一定是最高
的，而乱序是非常难调且收益不稳定但是成就感最高的哈哈。
6.3 备赛经验及建议
其实和备赛相关的经验在前文偶有提及，这里系统性总结一下，我认为我们的
整个路径对后来人的参考意义是非常大的，如果你们要从零开始，那么跟着我们的
路径实现可以少踩很多雷。
我们从寒假开始备赛，首先学习体系结构的基础知识——计算机组成原理，我
们跟着刘宏伟老师的课程学习，这个课程太过抽象，这里我推荐你们采用《软硬件
接口》这本书，用 MIPS 版本还是 RV 版本随意，不必全部学完，只需要把书中关
于流水线的部分全部认真学完，还有关于了解 CPU 在执行过程中的异常就行。
然后跟着《CPU 设计实战》这本书慢慢做，注意一定要选择 LoongArch 版本
（这本书还有 MIPS 版本，不推荐），如果不跟着《实战》做，直接对着指令手册
实现功能，那么极大可能被指令手册中一些表述不清的地方误导，23 年 Invalid 
Syntax 和 24 年春日影队都被这个问题困扰过。《实战》的编者毕竟就是龙架构首
席设计师，对 LA32R 中很多特权态的功能都做了更详细的阐述，配合着 openla500
- 44 -
一边看代码一边看书就能很好把握特权态指令的功能，少走很多很多弯路。
《实战》一开始的几个实验在网上（譬如 CSDN）都能找到答案，不妨参考这
些答案加快进度。完成所有用户态指令并且写完前递之后就可以开始分工了，在此
之前最好所有的队员都跟着《实战》做一遍。
完成《实战》中有关精确异常相关内容后，接下来是写类 SRAM 总线。此时
虽然还没有加入 cache，但是类 SRAM 总线的约定可以作为流水线和 Cache 之间
数据交互的规定。然后是在没有 cache 的情况下添加 AXI 总线的支持，不过此时
相当于直接从流水线的类 SRAM 总线设计转接桥连接 AXI 接口，实际上这没有必
要，因为之后所有的访存都要通过 cache 与总线进行交互，所以不妨在做完类
SRAM 总线后直接开始实现 cache+AXI 转接桥，虽然一步到位比较困难但是可以
避免重复的精力消耗（提示一下实现 cache 之后 AXI 转接桥可以直接把 openla500
的拿过来用，我们就是这样干的）。
做完设计实战之后继续通过 chiplab func19，此时就可以分两条线，用五级流
水实现系统启动，以及在此基础上改出超标量架构。
此时你可能会有点疑问，五级流水能启动系统，但是改了架构之后岂不是要重
新调试一遍吗？nonono，之前提到我们把 CPU 分为流水线和访存两个子系统，如
果 CPU 能启动系统说明访存以及异常处理这块基本上没有问题，而我们修改完新
架构之后肯定要跑性能测试，能通过性能测试的情况下又说明新架构的流水线其
实没有特别大的问题，如果只是改动前后端，基本上不会对以 Cache 为主体的访
存系统做太大修改。那么新架构完成之后相当于流水线和访存基本上都没什么大
的缺陷，此时用新架构启动系统是非常快速的，实际上也确实如此，我们在初赛提
交之前还没有尝试用双发的架构启动系统，初赛提交之后只花了两天就成功启动
了。
现在回过头来看，我们似乎每一步都走对了，一开始选择了最贴合 LA32R 的
《实战》来入门，进入 7 月后又很快接入了 chiplab 进行测试，并且直接奔着启动
系统去，初赛到复赛的性能优化也是挑了几个最容易收益也最大的地方。现在想想，
如果当初不沿着这条路走那么根本不可能在比赛之前完成这么大的工作量。
