## 1. 先给结论

如果目标是最终做出“乱序多发射、3级 cache、主频至少 75MHz”的 LoongArch32 核，那么最值得继承的组合是：

1. 前端优先吸收团队赛方案的思路：FTQ、FTB、TAGE、RAS、预译码、较宽取指。
2. 后端优先吸收 cpucore-mariver-main 的思路：重命名、ROB、发射队列、功能单元解耦、提交与异常恢复清晰。
3. 缓存体系优先吸收 open-la500 的工程化风格：模块边界清晰、时序保守、易于稳定收敛。
4. 研究性上参考 open-la1000 的参数化与超标量组织，但不要一开始就把复杂度拉满。

对当前 mycpu 来说，最重要的不是“马上把所有特性都加上”，而是先把未来的乱序化、多发射、3级 cache 的骨架搭稳。只要骨架搭对，75MHz 在 FPGA 上通常不是最难的指标，真正难的是正确性、恢复路径和时序闭环。

## 2. 五个设计的定位对比

| 设计 | 架构定位 | 前端特点 | 后端特点 | Cache / TLB | 优点 | 缺点 |
|---|---|---|---|---|---|---|
| 团队赛方案 | 超标量乱序核，前端很强 | 4-wide 取指，FTQ/FTB/TAGE/RAS，预译码较完整 | 双发射乱序，ROB + RAT + IQ + 多功能单元 | I/D cache 较完整，TLB 规模偏小但接口齐全 | 前端成熟，分支预测很强，整体性能潜力高 | 结构复杂，验证成本高，集成难度大 |
| cpucore-mariver-main | 乱序执行后端很强 | 前端相对传统，重点不在超强预测 | ROB / rename / station / FPU 等组织清晰 | 支持二级 TLB 思路，体系化程度高 | 后端非常适合做性能核，提交/重命名路径清晰 | 前端激进度一般，TLB 层次和规模需要权衡 |
| open-la500 | 官方稳健基线核 | 简洁前端，工程化强 | 单发射五级流水，容易收敛 | 32 项 TLB，I/D cache 设计成熟 | 稳定、易调试、易闭环，适合作为对照基线 | 单发射吞吐有限，性能上限低 |
| open-la1000 | 参数化超标量静态核 | 较强前端和参数化预测体系 | 超标量、参数化、适合做研究原型 | 参数化 TLB / cache，PA 可扩展到 36 位 | 架构弹性很强，适合作为方法论参考 | 验证复杂，设计自由度大也意味着风险大 |
| 当前 mycpu | 可继续演进的工程核 | 当前是标准五级流水，边界清晰 | 目前更适合逐步加入 OoO / 多发射能力 | 当前 TLB 为 32 位地址体系，表项规模为 16 项，I/D cache 与 AXI line bridge 已具备 | 结构干净，容易继续改造 | 现阶段吞吐还不够，内存层次和乱序基础需要补齐 |

## 3. 各设计的优点、缺点与可借鉴点

### 3.1 团队赛方案：前端是最大亮点

这个方案最值得学的是前端，不是单纯的“分支预测器更花哨”，而是它把前端拆成了可控的几个阶段：预测、目标队列、取指、预译码、重定向。它的价值在于把高复杂度的前端逻辑模块化了，方便继续加 uBTB、FTB、TAGE、RAS。

优点：

- 取指宽度较大，前端吞吐上限高。
- FTQ 作为前后端缓冲，能把前端预测和后端执行解耦。
- FTB 和 TAGE 组合非常适合做“方向预测 + 目标预测 + 取指块预测”。
- RAS 让函数调用/返回类分支的预测效果很好。

缺点：

- 设计复杂，任何一个预测模块出错都会把前端拉崩。
- 前端状态机多，回滚、重定向、训练路径长，调试成本高。
- 如果后端不够强，前端再强也会被后端吞吐限制住。

可借鉴点：

- 你的 mycpu 如果未来要做乱序多发射，前端一定要先升级；否则后端再强也喂不饱。
- 建议优先复用它的“前端分层思想”，不一定一开始就复用全部预测算法。

### 3.2 cpucore-mariver-main：后端组织非常值得抄

这个方案的核心价值在后端。它把 rename、ROB、station、commit、FU 这些结构都做成了较独立的功能块，很适合做性能核的骨架。

优点：

- 后端流水组织清晰，适合做乱序执行的教学/工程原型。
- 重命名和发射站的职责分明，利于扩展到多发射。
- 对浮点、乘除、访存等单元的拆分思路成熟。

缺点：

- 前端不算激进，和强后端相比，前端可能成为性能瓶颈。
- TLB 思路偏保守，层次和规模需要根据目标系统重新设计。
- 如果要追求更高主频，还要继续拆分关键路径。

可借鉴点：

- mycpu 后续要做 OoO，最重要的是把“指令流入后端后的状态变化”做成可恢复的。
- ROB、rename、issue queue、commit 这四件事要先设计好恢复语义，再考虑多发射数量。

### 3.3 open-la500：最适合作为稳态基线

open-la500 的价值不在“性能最强”，而在“稳、清楚、能跑、好闭环”。这种设计很适合作为当前 mycpu 改造时的工程基线。

优点：

- 五级流水清晰，调试和验证成本低。
- 单发射架构容易保证时序。
- 32 项 TLB 规模相对更充裕，适合一般 32 位系统场景。
- cache、AXI、TLB、CSR 的边界清楚，便于移植。

缺点：

- 单发射限制了 IPC，上限不高。
- 前端预测较朴素，对分支密集代码不占优。
- 若想上更高性能，需要在前端和后端都做较大改造。

可借鉴点：

- 适合保留它的“工程稳态”思想：模块接口少而清楚，少做隐式耦合。
- 对于 mycpu 当前版本，先保证功能和时序，后再引入乱序和多发射。

### 3.4 open-la1000：更像“方向图”，不是现成答案

open-la1000 的最大特点是参数化和超标量思路。它适合用来学习“怎样把核写成可配置平台”，而不是直接照抄每个模块。

优点：

- 参数化能力强，适合在不同 FPGA / ASIC 场景下调整。
- 分支预测、TLB、缓存都更像研究平台。
- 结构上更接近“可扩展超标量核”的表达方式。

缺点：

- 参数化带来验证复杂度，边界情况非常多。
- 设计自由度大，容易把时序和功能一起做复杂。
- 对初期团队来说，直接照搬会比想象中更难收敛。

可借鉴点：

- mycpu 如果要走向多发射和三级 cache，最好先把参数都抽象出来，至少把发射宽度、cache 容量、TLB 项数、PA 宽度、分支预测器配置做成统一配置层。

## 4. mycpu 现在到底处于什么位置

从当前顶层和 mmu/cache 代码看，mycpu 现在更像是一个“边界已经比较完整的五级流水工程核”，而不是成熟的乱序核。

### 4.1 现在已有的基础

- 顶层是 IF / ID / EXE / MEM / WB 五级结构。[mycpu_top.v](output/vivado_cpu_origin/myCPU/top/mycpu_top.v)
- 已经有 MMU / TLB / ICache / DCache / AXI line bridge 的完整链路。[tlb.v](output/vivado_cpu_origin/myCPU/common/mmu/tlb.v) [axi_line_bridge.v](output/vivado_cpu_origin/myCPU/common/mmu/axi_line_bridge.v)
- 已经有 cache control unit，说明缓存维护指令、I/D cache 控制已经从桥接层里分离出来。[cache_control_unit.v](output/vivado_cpu_origin/myCPU/common/mmu/cache_control_unit.v)
- 当前 TLB 接口是 32 位虚地址体系，vppn 为 19 位，asid 为 10 位，ppn 为 20 位，属于典型的 LoongArch32R 设计方式。[tlb.v](output/vivado_cpu_origin/myCPU/common/mmu/tlb.v)

### 4.2 当前的主要短板

- 仍然是典型顺序流水，IPC 上限低。
- cache / AXI 的关系还偏“桥接式”，更像是 cache 下面挂一个传输层，而不是 cache 主导整条内存层级。
- TLB 规模只有 16 项，和更激进的参考方案相比还不够大。
- 前端缺少更完整的多级预测与取指队列体系，遇到分支密集代码时容易掉性能。

### 4.3 你问的关键点：mycpu 的 TLB 也是 32 位吗

是的，按当前实现看，mycpu 也是 32 位地址体系，不是 64 位。

更准确地说：

- 虚地址为 32 位体系。
- TLB 里用于查找的 vppn 是 19 位。
- asid 是 10 位。
- 物理页号 ppn 是 20 位。
- 这与 open-la500 的 32 位 LoongArch32R TLB 模式是一致的，差别主要在 TLB 表项数量和后续的系统组织，而不是“是不是 32 位寻址”。

## 5. mycpu 接下来的改进方向

下面给的是我建议的优先级，不是“一口气全做”的清单。

### 5.1 第一优先级：先把内存层次和桥接关系改对

你提到的两点“增大 cache”和“不要 SRAM-AXI 转接桥，改成 cache-AXI 转接桥”，我认为都应该采纳。

原因很直接：

- 现在真正卡性能的，往往不是 ALU，而是取指和访存。
- 如果 AXI 桥只是把 SRAM 风格接口翻译一下，那么 cache 还是被动的一层，难以扩展成真正的层次结构。
- cache-AXI bridge 应该服务于 cache line 的填充、回写、失效和并发请求，而不是服务于“单次读写一个 SRAM 单元”。

建议：

- ICache / DCache 改成以 cache line 为单位的请求接口。
- AXI bridge 只负责 line fill / line writeback / burst arbitration。
- 引入 MSHR 或至少引入请求跟踪表，避免 miss 时把整个流水彻底锁死。
- 先把 L1 做大、做稳，再考虑 L2 / L3。

### 5.2 第二优先级：前端升级，先让核“喂得进去”

如果后端要乱序多发射，前端必须先升级，否则后端会长期空转。

建议前端路线：

1. 先把预测器做成“基础预测 + 目标修正 + 训练回写”的三段式。
2. 参考团队赛方案引入 FTQ，用来缓冲预测块和重定向信息。
3. 取指宽度至少做到 4 指令级别的“逻辑宽度”，即使后端先只接受 2 发射也没问题。
4. 预译码要保留，把强制跳转、调用、返回、访存对齐类信息尽量前移。
5. 分支预测器优先级建议是：简单 BTB / uBTB -> FTB -> TAGE -> RAS。

这样做的好处是：

- 先把高频热点分支处理好。
- 让前端和后端之间有足够缓冲，不至于因为一次 miss 或一次重定向就整核抖动。

### 5.3 第三优先级：后端从“顺序”过渡到“乱序”

这是最关键的一步，也是最容易一次做崩的一步。建议按阶段推进，不要一步到位。

推荐的演进顺序：

1. 先做寄存器重命名。
2. 再做 ROB。
3. 再做 issue queue / station。
4. 再做 wakeup-select / forwarding / commit 恢复。
5. 最后再把多发射从 2-wide 扩展到更高宽度。

最重要的设计原则是：

- 每条指令进入 ROB 时，必须能唯一定位它的退休状态。
- 分支错判、异常、TLB refill、cache miss、CSR 访问都必须有明确的清空/回滚规则。
- 先实现“正确的双发射乱序”，再追求“更宽的多发射”。

### 5.4 第四优先级：把三级 cache 设计成可收敛的结构

如果目标是 3 级 cache，我建议不要把三级 cache 理解成“简单加三层 SRAM”。更合理的做法是：

- L1：小而快，分 I/D，优先追求命中延迟。
- L2：统一或半统一，承担大部分 miss 吸收。
- L3：作为共享后备层，更多负责减少最坏情况的外部访问压力。

在 FPGA 场景里，三级 cache 的现实做法通常有两种：

1. 真正的三级缓存，但每一级都要做严格的流水化与 bank 化。
2. L1 + L2 + victim / buffer 级别的“逻辑三级”，把最后一级做成容量后备而非极致低延迟。

对于你现在的目标，我更建议先做“L1 + L2 + L3 后备层”，不要一开始就追求极深的相联度和极低延迟，否则时序会非常难看。

### 5.5 第五优先级：为 75MHz 预留时序空间

75MHz 不是一个很激进的频率，但在乱序、多发射、三级 cache、TLB、分支预测同时存在的情况下，真正的挑战是关键路径。

重点要拆的路径有：

- 取指路径：PC -> 预测 -> TLB -> ICache tag compare -> 取指返回。
- 数据路径：EXE -> 地址生成 -> TLB -> DCache tag compare -> 读写返回。
- 旁路路径：EXE/MEM/WB -> forwarding -> issue 决策。
- 控制路径：异常 / 分支错判 / refetch / flush。

建议的时序策略：

- 把预测、TLB、cache tag compare、数据返回分成至少两个阶段。
- 关键比较器和多路选择器尽量局部化，别把全局控制链拉得太长。
- 对于高扇出控制信号，用寄存器切断或局部复制。

## 6. 一个可执行的演进路线图

### 阶段 A：把现有 mycpu 固化成稳定基线

目标：保证现有五级流水稳定、功能正确、时序可控。

- 完善 TLB / cache / AXI 的错误处理和调试信息。
- 统一 refetch、flush、exception、cache maintenance 的优先级。
- 确认 I/D cache 的 miss 行为不会把流水线锁死。

### 阶段 B：做“增强前端 + 更大 cache”

目标：先让性能有明显提升，但不改变后端基本模型。

- 增大 L1 cache。
- 引入 cache-AXI bridge。
- 引入更强的前端预测模块和 FTQ。
- 先把取指宽度提高到 4 的逻辑目标。

### 阶段 C：从顺序核过渡到双发射乱序核

目标：建立 OoO 的基本骨架。

- 增加 rename、ROB、issue queue、wakeup-select。
- 将执行单元拆分为普通 ALU、分支、访存、乘除等几类。
- 做好异常精确提交。

### 阶段 D：扩展到更宽的多发射，并引入更深 cache 层次

目标：在稳定性不掉的前提下继续提性能。

- 从 2-wide 扩到 3-wide 或 4-wide，再看布线和时序情况。
- 引入 L2 / L3 层次，优化 miss 吸收能力。
- 增强预取、victim cache、非阻塞 cache 等能力。

## 7. 最后给一个判断

如果你想把 mycpu 做成真正有竞争力的作品，我建议路线不要是“只堆复杂度”，而应该是：

1. 先把前端做强。
2. 再把后端乱序化。
3. 再把 cache 层次加深。
4. 最后做时序收敛和系统整合。

这条路线的核心逻辑是：

- 前端决定核能不能持续喂饱。
- 后端决定 IPC 上限。
- cache 决定真实工作负载下的性能上限。
- 时序决定这一切能不能在 FPGA 上真正跑到 75MHz。

如果只选一句话作为总纲，我建议是：

**用团队赛方案的前端思路，结合 cpucore-mariver-main 的后端思路，再用 open-la500 的工程稳态去收口，最后把 mycpu 逐步演进成可参数化的乱序多发射三层缓存核。**
